# Firestore Security (current constraints)

Этот документ описывает, что реально защищается в проекте сейчас, без изменений клиента и схемы данных.

## Текущий контекст

- Авторизация: Firebase Auth (anonymous).
- Членство в списках: `lists/{listId}.members` хранит email-строки.
- В rules нет надёжного способа доказать соответствие `request.auth` конкретному email из `members`, потому что при anonymous auth email отсутствует в `request.auth.token`.

Следствие: полноценная membership-based авторизация "по email из members" в текущей архитектуре невозможна.

## Что реализовано в `firestore.rules`

1. Доступ только для аутентифицированных сессий:
- Для рабочих путей чтение/запись требуют `request.auth != null`.

2. Явно разрешены только нужные пути:
- `lists/{listId}`
- `users/{userId}`
- `shopping/catalog`
- Любые другие пути запрещены.

3. Валидация top-level схемы и типов:
- `lists/{listId}`:
  - только поля `name`, `members`, `items`;
  - `name` ограничен по длине;
  - `members` должен быть непустым массивом;
  - `items` должен быть `map` или `list` с лимитом размера.
- `users/{userId}`:
  - только поля `email`, `name`, `updatedAt`;
  - обязательны `email`, `name`;
  - `updatedAt` только number (если присутствует);
  - на update `email` неизменяем.
- `shopping/catalog`:
  - доступен только документ `catalog`;
  - только поле `entries`;
  - `entries` должен быть `list` или `map` с лимитом размера.

4. Минимизация прав записи:
- `users` и `shopping/catalog`: удаление запрещено.
- `lists`: разрешены create/update/delete (нужно для текущего клиента), но с валидацией структуры.

## Известные ограничения безопасности

Невозможно корректно выразить правило вида:
- "читать/писать список может только пользователь, чей email входит в `members`".

Причина:
- anonymous auth не предоставляет проверяемый email/uid-mapping для `members` (email-строк).

Текущие rules снижают риск за счёт:
- закрытия лишних путей,
- ограничения формата документов,
- запрета части операций,
но не обеспечивают полноценную изоляцию данных между участниками.

## Что нужно для полноценной membership-безопасности

Один из вариантов (рекомендуется):

1. Перейти с anonymous auth на аутентификацию с проверяемой идентичностью:
- Firebase Auth email/password, magic link, OAuth и т.п.

2. Привязать членство к проверяемому идентификатору:
- хранить в списке `uid` участников (или поддерживать проверяемый mapping `uid -> email`).

3. Обновить rules на membership-проверки:
- доступ к `lists/{listId}` только если `request.auth.uid` присутствует в members;
- доступ к пользовательскому профилю только к собственному документу.

4. Для чувствительных операций использовать серверный контур:
- Cloud Functions/Admin SDK для инвайтов, миграций membership, привилегированных обновлений.

## Операционная заметка

После изменения `firestore.rules` их нужно задеплоить в Firebase проект:
- `firebase deploy --only firestore:rules`

Без деплоя локальные изменения в репозитории не применяются в проде.
